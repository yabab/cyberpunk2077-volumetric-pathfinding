# PathfindingUpdate — volumetric 3D pathfinding for Cyberpunk 2077

A RED4ext plugin and reusable C++ library that plans paths through **open 3D space** for **flying
agents**. Sync and async APIs, thread-safe by construction.

Cyberpunk ships nothing that can do this. Its entire navigation stack is a walkable navmesh —
`NavGenAgentSize` has exactly one value (`Human`), every path call is literally named
`...OnlyHumanNavmesh`, and there is no volumetric representation anywhere in the reflected type
set. So this library builds its own free-space map and searches that. See `DESIGN.md` for the
full rationale and architecture.

It gets that map two ways, layered:

1. **A baked static world**, extracted offline from the game archives. This is the authority.
2. **Runtime physics probes**, which handle what the bake cannot know about — doors, vehicles,
   destruction.

The bake is not an optimisation. The physics scene only contains collision for sectors that are
**currently streamed in**, so a probe 400 m away returns *empty air* for a building that has not
loaded — not a slow answer, a wrong one. Reading the archives sees the whole map at once.

**Status: v0.1.0.** The engine-agnostic core and the full offline bake pipeline are implemented
and covered by 625 passing offline tests. The plugin has run in-game: it loads, registers,
attaches to the fast RTTI probe path, and shuts down clean. A live path query end-to-end is still
pending — see [Verification status](#verification-status).

## Building

Requires Visual Studio (MSVC) and CMake ≥ 3.21. Both ship with VS; no separate install is
needed. The generator must match the installed VS — on the current machine that is
"Visual Studio 18 2026" (the older "Visual Studio 17 2022" recipe below the fold of git history
was for a previous install).

```powershell
# One-time: fetch the SDK (not vendored - it is ~10k files)
git clone https://github.com/WopsS/RED4ext.SDK.git myMods/PathfindingUpdate/vendor/RED4ext.SDK

$cmake = "C:\Program Files\CMake\bin\cmake.exe"
$src   = "C:\Code\games\cyberpunk2077modding\cyber2077mods\myMods\PathfindingUpdate"

& $cmake -S $src -B "$src\build" -G "Visual Studio 18 2026" -A x64
& $cmake --build "$src\build" --config Release
```

> **Re-pin the SDK on every game patch.** `vendor/RED4ext.SDK` is a git clone — `git fetch` and
> check out the newest commit whenever the game updates. The plugin is *compiled against the
> game's ABI*: patch 2.5 alone changed `CBaseFunction` (0xB0 → 0xF0), `CStackFrame` (0x68 → 0xA8),
> `CGameEngine`'s field offsets (`framework` 0x308 → 0x348), grew `IRTTISystem`'s vtable, and
> re-pointed the SDK's address hashes — plus `RED4EXT_V1_RUNTIME_VERSION_LATEST`, which the plugin
> declares in `Query()` and which RED4ext checks at load. A DLL built against a pre-patch SDK is
> quietly wrong at runtime (or refused outright); a rebuild against the new SDK is mandatory and
> is not optional churn. The engine-agnostic `vnav_core` never changes for a game patch — only the
> SDK pin and the rebuild do.

If `build/` contains a `CMakeCache.txt` from another machine (e.g. after a workspace migration),
delete the whole `build/` directory and configure again — CMake refuses to reconfigure across a
moved root and a stale cache also pins a VS install path that may no longer exist.

Three targets:

| Target | Output | Notes |
|---|---|---|
| `vnav_core` | `vnav_core.lib` | Engine-agnostic. **Zero** RED4ext/game includes. |
| `PathfindingUpdate` | `PathfindingUpdate.dll` | The plugin. Auto-staged into `code/red4ext/plugins/`. |
| `vnav_tests` | `vnav_tests.exe` | Runs standalone against a synthetic world. |

Run the tests — they need no game, no RED4ext, and no world:

```powershell
& "$src\build\Release\vnav_tests.exe"   # exit 0 == pass
```

## Deploying

The build stages the DLL automatically. Then:

```powershell
powershell -File myMods\deploy.ps1 -ModName PathfindingUpdate
```

Staged layout (mirrors the game root):

```
code/
├── red4ext/plugins/PathfindingUpdate/
│   ├── PathfindingUpdate.dll          0.4 MB
│   └── nightcity.vnavbake           173.4 MB   ← ships; see below
└── r6/scripts/PathfindingUpdate/VolumetricNav.reds
```

**The bake ships with the mod.** The plugin can technically run without it, but only by probing —
which cannot see un-streamed geometry, so long-range paths would be wrong. It is not in git
(173 MB, past GitHub's 100 MB per-file limit) and is regenerated by the two commands above, so a
fresh clone must bake once before the mod does anything useful.

The bake is a snapshot of the geometry in one game version. That is an accepted risk rather than
an oversight: Cyberpunk's updates have stopped, and if a patch ever did change world geometry it
would break essentially every mod in a load order anyway — a rebake and re-ship is already on the
critical path for that scenario.

> `deploy.ps1` gained a `red4ext\plugins` category for this mod — it is the workspace's first
> native plugin. The change is additive and affects no existing mod.

## Baking the static world

Two steps, both offline. Nothing here runs while the game does.

**1. Extract collision from the archives** — a `navbake` command added to WolvenKit's CLI
(branch `feature/navigation-baker`). It walks every `.streamingsector`, parses the compiled
collision buffers, resolves mesh shapes through the geometry cache, and writes every shape in
world space to a `.vnavgeo`:

> **Game patch 2.5 re-cooked the world.** Sectors no longer carry `worldCollisionNode`; collision
> now lives in the `worldCookedCollisionNode` family (`worldCookedCollisionNodeBuffer` — actors,
> shapes, and shared position/rotation/scale/preset tables — plus a sibling info buffer carrying
> each logical node's LOD and sector hash). Mesh shapes are keyed by `(sectorHash, hash)` into the
> same `physicsGeometryCache` as before, so geometry resolution is unchanged. The extractor reads
> **both** generations (`NavGeometryExtractor`), so it works against pre- and post-2.5 archives.
> If a future patch re-cooks again, the histogram at the end of a run is the tell: `Collision
> nodes: 0` with all sectors scanned means the node type moved again.

```powershell
WolvenKit.CLI.exe navbake -o nightcity.vnavgeo -g "C:/Program Files (x86)/Steam/steamapps/common/Cyberpunk 2077"
```

Useful flags: `--filter <substring>` and `--maxSectors <n>` for a quick subset, `--lod <n>` to
take one LOD, `--excludePresets a,b` to drop collision presets. Every run prints histograms of
shape type, collision preset and LOD — those are there because the field semantics in the
compiled buffer are *not* the same as the script-facing enums, and the histogram is how you find
that out rather than assuming.

Full-map extraction, measured (patch 2.5, base game + Phantom Liberty — 28m37s, 1.42 GB):

```
47,987 sectors scanned, 27,427 with collision, 0 failed
498,820 collision nodes | 16,193,685 actors | 20,010,490 shape instances
146,351 unique meshes (14,846,490 triangles), 11 unresolved
Box 7,290,326 | TriangleMesh 7,906,550 | Sphere 2,814,774 | Capsule 1,126,634 | ConvexMesh 872,206
world bounds (-7687, -7381, -765) .. (7184, 6141, 2254)
```

The pre-2.5 extraction (patch 2.3: 47,950 sectors / 27,385 with collision / 19,965,961 instances /
11 unresolved) is kept as `bake/nightcity-2.3.vnavgeo` and was diffed voxel-by-voxel against the
2.5 bake at 1 m with `vnav_bake --compare`: **508,112,069 solid voxels in both (100.0% of each),
4,012 only in 2.3, 59,001 only in 2.5.** World geometry is effectively unchanged between those
patches — but the shipped bake is re-extracted from the current archives regardless, so that is a
measurement rather than an assumption.

The preset histogram immediately earned its place: alongside `World Static` (10.8M) and
`Complex Environment Collision` (2.6M) there is a preset literally named **`No Collision`**, plus
`Shooting` and `Window` which are plausibly shoot-through rather than solid. They are tiny
(71 / 586 / 353 shapes out of 20M), so they are not worth a re-extract on their own, but the
recommended exclusion for a clean run is:

```
--excludePresets "No Collision"
```

**2. Voxelise it — straight into the shipped location.**

`vnav_bake` writes wherever you point it, so point it at the staged folder rather than baking
somewhere else and copying. A copy step is a step that eventually gets skipped, and the symptom
would be a shipped mod quietly running on a stale bake:

```powershell
vnav_bake.exe bake/nightcity.vnavgeo `
              code/red4ext/plugins/PathfindingUpdate/nightcity.vnavbake --voxel 1.0 --gamebuild 2.5
```

`--gamebuild` stamps the bake with the game build its geometry was extracted under. The plugin
can then refuse a stale bake at attach time (`VNavAttachBakeChecked`) instead of planning
confidently through geometry that a patch has moved — see "Known limits" for what an unstamped
bake costs. The value is just a string compared for equality against whatever the caller passes
as the expected build; use the game's product version (e.g. `2.5`).

The `.vnavgeo` stays in `bake/` — it is a 1.4 GB intermediate, never shipped, and worth keeping
so the voxeliser can be re-run at another resolution without another 37-minute extract.

Full map, measured:

```
40,498 tiles                                                    31 seconds
632,485 mixed chunks | 26,261 solid | 1,933,126 open (not stored)
263 bytes per mixed chunk (raw would be 4096)
chunk range (-484, -464, -48) .. (451, 383, 143)
```

**173 MB for all of Night City at 1 m voxels.**

**3. Check it without launching the game:**

```powershell
vnav_bake.exe --inspect code/red4ext/plugins/PathfindingUpdate/nightcity.vnavbake --at -1500,-800,5
```

`--inspect` reads the bake back through the same loader the game uses, so it exercises the
distance transform too, and prints a vertical clearance column — a cross-section of the world at
that point:

```
  point (-1500.0, -800.0, 5.0) -> chunk (-94, -50, 0)
  of 4096 voxels: 256 solid, 3626 within 8 voxels of something, 214 wide open
  clearance column at that x,y (bottom to top of chunk):
    ..  7  6  5  4  3  2  1 ##  1  2  3  4  5  6  7
```

Open air below, a solid deck, open air above — and the clearance falling off monotonically on
both sides of it. Other sampled points show ground with an overhang above, a floor slab inside a
building, and open sky over a street. That is what a correct bake looks like.

Then point a volume at it, from redscript:

```swift
VNavAttachBake(n"drone", "red4ext/plugins/PathfindingUpdate/nightcity.vnavbake");
```

### What the bake stores, and why it isn't clearance

The planner wants **clearance** — distance to the nearest solid — because that is what makes the
data agent-agnostic: "does a radius-r agent fit here" becomes one threshold compare, so a single
bake serves a drone and an AV alike.

Storing clearance directly was implemented, measured, and rejected. A clearance field is a
*gradient*, and in a city almost every voxel is on one, so it barely compresses — **1819 bytes per
chunk**, projecting to multiple GB for the map at 1 m voxels.

So the bake stores **occupancy**, one bit per voxel, and the distance transform runs at load
time. Same measurement: **227 bytes per chunk**, an 8× reduction, and the bake itself got 5×
faster because it no longer transforms anything.

It is also *more* accurate. A stored field has to saturate at some cap; the load-time transform
reaches exactly as far as the asking volume's own threshold, so there is no saturation to lose
information to and no global limit on agent size.

| | bytes / mixed chunk | mixed chunks | full map, projected |
|---|---|---|---|
| clearance field, cap 15 | 1819 | 36,690 | multiple GB |
| clearance field, cap 4 | 859 | 17,522 | ~1.5 GB |
| **occupancy + load-time transform** | **227** | **12,317** | **173 MB (actual)** |

*(200-sector sample at 1 m voxels; the last column is the measured full-map result)*

## Testing it in-game (VNavTest)

A CET harness ships in `code/bin/x64/plugins/cyber_engine_tweaks/mods/VNavTest/`. It exists
because tuning agent radius is the point, and redscript would need a restart per change — here a
slider re-plans live. That is only cheap *because* the bake stores occupancy: changing radius
re-derives clearance from the same chunks instead of re-probing the world.

The panel is ordered so each section only makes sense once the one above it is green. **Work down
it.** Whatever is the highest red section is where the problem is:

| Section | Proves |
|---|---|
| 1. Plugin | the DLL loaded and registered its natives |
| 2. Volume + bake | the bake attached and covers where you're standing (`chunks from bake` climbing) |
| 3. Plan | a query returns at all — status, points, length, detour ratio |
| 4. Draw | the route is geometrically sane in the world |
| 5. AV | fly something along it |

**The single most useful control is "draw agent radius rings."** Each ring is drawn at the
agent's actual radius, so a ring that visibly clips a wall means the clearance threshold and the
geometry disagree — which is the bug worth catching, and it is invisible in a line-only view.

**Suggested order**, matching where the risk actually is:

1. **Badlands, goal follows player, small radius.** Open sky, few surfaces. If this fails, the
   problem is the plugin or the bake, not the search.
2. **Badlands, radius up to 4–6 m.** Watch `detour` — it should stay near 1.0x in open ground. A
   large detour out there means over-blocking, and the first suspect is the LOD union (see Known
   limits).
3. **City streets.** The real test. Watch for routes that cut a building corner (under-blocking,
   serious) versus routes that refuse a gap you can see is wide enough (over-blocking, usually
   LOD or the half-voxel conservatism).

The AV moves **kinematically**, by teleport, on purpose — vehicle AI would fight the path and
make it impossible to tell a bad route from a bad driver. It plans from the AV's own position
once spawned, not the player's.

Note the AV record name is a guess and differs between versions and installed mods; the harness
has a **Find AV records** button that scans TweakDB for what your install actually has. Spawning
needs Codeware for `DynamicEntitySystem`. Sections 1–4 need neither.

## Using it from redscript

> **Building on vnav?** [`docs/INTEGRATION.md`](docs/INTEGRATION.md) is the full integration
> reference — every function on every surface (redscript, CET Lua, C ABI, C++), all defaults,
> runnable recipes, and the contracts to read before shipping. The snippets below are the quick
> tour.

```swift
// One volume per agent profile. Agent radius is baked into the sampled data, so a drone and an
// AV want two volumes, not one.
VNav.CreateVolumeAround(n"drone", playerPos, 300.0, 1.0, 0.5, 1.0);
//                       name     centre     halfExtent voxel radius margin

// Async is the intended path: it plans on worker threads and samples the world a frame at a time.
let handle: Uint32 = VNavFindPathAsync(n"drone", startPos, goalPos);

// ... later, poll (typically from an update or a DelaySystem callback):
let status: Int32 = VNavPathStatus(handle);
if VNav.IsTerminal(status) {
  if VNav.IsUsable(status) {
    let points: array<Vector4> = VNav.GetPoints(handle);
    // fly along `points`
  };
  VNavPathRelease(handle);
};
```

`PartialSuccess` is a usable result on purpose: a flying agent that gets 80% of the way to an
unreachable goal is far more useful than one that refuses to move.

When the world changes — a door opens, something is destroyed, a vehicle moves — tell the
library, or it will keep planning against stale geometry:

```swift
VNavInvalidateBox(n"drone", doorPos, new Vector4(5.0, 5.0, 5.0, 0.0));
```

## Using it from another RED4ext plugin

`include/vnav/vnav_capi.h` declares a plain-C ABI, so a consumer binds by `GetProcAddress`
without matching our MSVC version or STL ABI. Note the C ABI covers **core planning** — the
checked-bake attach, per-volume tuning (including the 4D search), escape/unstick and the
dynamic-obstacle layer are redscript-only or reachable by linking `vnav_core`;
[`docs/INTEGRATION.md`](docs/INTEGRATION.md) §6 lists the boundary exactly:

```cpp
auto getApi = (VNav_GetApiFn)GetProcAddress(GetModuleHandleW(L"PathfindingUpdate.dll"), "VNav_GetApi");
auto* api   = (const VNav_Api_v1*)getApi(1);

VNav_QueryDesc q;
api->QueryDescDefaults(&q);       // always start from defaults, then override
q.start = {...}; q.goal = {...};

uint32_t h = api->SubmitAsync("drone", &q);
```

Or link `vnav_core` directly and use `include/vnav/NavService.hpp` if you want the C++ API and
can accept the ABI coupling.

## Threading

The one hard rule: **`IWorldProbe` may only be called on the game thread**, because REDengine
drives PhysX on its own schedule and scene queries from an arbitrary thread race the simulation
step. Everything else is free.

| Thread | May do |
|---|---|
| Game | `Pump()` (which is the only thing that probes), completion callbacks |
| Workers (1–4) | Search only. Never touches the game. |
| Any | Submit, poll, cancel, create/destroy volumes |

Two invariants carry the design:

1. **Chunks are immutable after publication**, held behind `shared_ptr<const Chunk>`. Invalidation
   replaces the pointer; it never mutates the payload.
2. **A job pins every chunk it reads** for its whole lifetime, so its view of the world is
   self-consistent and nothing it is walking can be evicted underneath it.

This is the C++ expression of the same lesson the redscript side of this workspace paid for the
hard way (`reference_redscript_shared_array_scan_crash`): never walk shared mutable state, hold
one handle to something immutable.

`TestConcurrentSubmitters` exercises exactly this — six threads submitting against two volumes
while the main thread pumps.

## Verification status

**Verified offline (625 checks):** coordinate math, adaptive sampling, Lazy Theta\* search,
corner-cut prevention, endpoint snapping, partial paths, suspend/resume, async round-trip,
cancellation, invalidation, bad-input rejection, no-world degradation, concurrent submitters,
sync-off-game-thread, and shutdown with jobs in flight.

For the bake specifically:

- **`TestBakeCodec`** — exact round-trip over uniform, sparse, striped and pseudo-random
  occupancy, including the raw fallback. A wrong bit here is a wall that isn't there, or worse
  one that's missing.
- **`TestBakedNav`** — load-time clearance checked against **brute force over every solid
  written**, not against itself. Specifically covers the halo reaching *across a chunk boundary*,
  which is the part most likely to be silently wrong. Also covers the three-way distinction
  between stored, absent-but-in-region (open sky), and outside-the-region (`nullptr`, so the
  caller probes instead of assuming clear).
- **`TestBakedRoutingWithoutProbe`** — routes through a wall's window with **no probe attached at
  all**, asserting `totalProbes == 0`. This is the streaming-independence claim, tested.

The bake side is validated against reality rather than assumption: **0 of 47,987 sectors failed
to parse**, 11 of 146,351 meshes failed to resolve (0.008%), and `--inspect` cross-sections
through the finished bake show ground planes, floor slabs, overhangs and open sky with clearance
falling off monotonically on both sides of every surface.

**Verified in-game (2026-08-15, first run).** The plugin logs its own lifecycle to a dedicated
`red4ext/logs/pathfindingupdate-*.log` — separate from `gamelog.log`, which only carries
`LogChannel`/redscript output and will show nothing for a RED4ext-native plugin. A first session
logged:

```
loaded
script bindings registered
running; probe ready (QueryFilter path)
world detached; dropping cached chunks
shutting down
```

That settles the two things the offline tests could not:

- **RED4ext's Running-state `OnUpdate` fires per frame** — confirmed; reaching `running` depends
  on it.
- **`physicsQueryFilter::AddGroup` resolves through RTTI** — confirmed directly by
  `(QueryFilter path)`. The ~4× slower per-group fallback never engaged.

Shutdown was clean: world detached and cached chunks dropped in order, no crash, no hang.

**Still open:** a live path query end-to-end (submit → poll → usable points) and real probe cost
per chunk under gameplay conditions, both blocked so far by a bug in the CET test harness
(`VNavTest`), not the plugin — see below.

`VNavStat(n"usingFilterPath")` and `VNavStat(n"nativePump")` report the same two facts at
runtime, for scripted checks that don't want to depend on log scraping.

## Measured costs (synthetic, from the test suite)

| Situation | Probes per chunk |
|---|---|
| Open sky | **1** — the octree early-out collapses the whole chunk |
| One plane through the chunk | ~730 at full 1-voxel resolution |
| Dense geometry | budget-capped, resolves to solid (which is the correct answer) |

Sampling refines **breadth-first**, so running out of budget degrades the whole chunk to a
coarser, uniformly conservative map. It never seals off an arbitrary octant — an earlier
depth-first version did exactly that and walled up a doorway.

Every failure mode over-blocks rather than under-blocks. An agent may fail to find a tight path;
it will never be routed through geometry.

## Known limits (V1, deliberate)

- **All collision LODs are baked — now VERIFIED as the right call.** Sector collision nodes carry a
  `lod` field. Over the full map: **lod0=42,606, lod1=335,783, lod2=119,781** — so LOD 1 is
  overwhelmingly the norm and filtering to LOD 0 would discard ~90% of the world's collision. The
  bake takes every LOD and unions them.

  This section previously called that union "the single most likely source of paths that detour for
  no visible reason", on the theory that higher LODs might be *coarser stand-ins* for the same
  geometry — a coarse box sealing an archway LOD 0 leaves open. **Measured, and it does not
  reproduce.** Same 400 sectors extracted three times with `--lod`, baked at 1 m, and diffed
  voxel-by-voxel with `vnav_bake --compare`:

  | comparison | solid voxels A | solid voxels B | overlap |
  |---|---|---|---|
  | LOD 0 vs LOD 1 | 1,366,230 | 4,511,199 | **8.3%** of LOD 0 |
  | LOD 2 vs LOD 1 | 104,252 | 4,511,199 | **20.0%** of LOD 2 |

  The LODs describe largely **different** geometry rather than the same geometry at different
  fidelity, so unioning them is correct and dropping any one would leave real collision unbaked.
  LOD 2 is also tiny — 2.3% of LOD 1's volume — so it contributes little either way.

  Remaining caveat, stated because the measurement does not cover it: this compares the LODs
  against *each other*, which rules out "LOD 1 seals what LOD 0 leaves open". It cannot rule out a
  given LOD being coarse in areas where it is the *only* source, because there is no ground truth
  to compare against there.
- **Underground reads as open where no collision exists.** Terrain is a surface, not a volume, so
  there is nothing solid beneath it. This is harmless for a flying agent — the surface is closed,
  so a search from valid free space cannot cross it — but a start point placed below ground will
  not be walled in.
- **Static world between invalidations.** Nothing rebuilds automatically when a door opens.
- **Bidirectional costs ~2× on short hops.** On by default (`PathQuery::bidirectional`), because
  the long-route case is where searches were failing outright. Measured offline:

  | route | unidirectional | bidirectional |
  |---|---|---|
  | 50 m, one offset window | 4,606 expansions | 8,686 expansions |
  | 640 m slalom | **PartialSuccess** — 2,000,000 expansions, never reached the goal | **Success** — 1,304,801 |
  | goal sealed in a box | `BudgetExhausted` at 60,000 — "gave up" | `Unreachable` at 11,605 — a real answer |

  Two frontiers each explore a comparable volume, so a short hop genuinely costs about twice as
  much; the win only appears once a single frontier has to grow as a large sphere. The absolute
  cost of the short-path penalty is small (both figures are sub-millisecond) while the long-path
  case is the difference between working and not, hence the default. Turn it off per volume with
  `VNavSetBidirectional` if a workload is overwhelmingly short hops.
  An automatic straight-line-distance threshold would get both, but two data points is not enough
  to site it, so it is deliberately not implemented.
- **No hierarchical graph — measured ceiling ~250 m.** Long paths are bounded by `maxExpansions`
  (default 60000) and return partials. Measured in-game 2026-08-15 over a 489 s chase, as
  `PartialSuccess` rate against straight-line distance to goal:

  | distance | partial rate | | distance | partial rate |
  |---|---|---|---|---|
  | 0–50 m | 4.9% | | 150–200 m | 16.3% |
  | 50–100 m | 1.7% | | 200–250 m | 49.2% |
  | 100–150 m | 9.4% | | 250–350 m | **100%** |

  Past ~250 m nothing completes. The ceiling is the **expansion budget, not distance** — the
  350–400 m bucket drops back to 45%, because open badlands expands far fewer nodes per metre
  than dense city. Budget for roughly 150 m in built-up areas and considerably more in open air.
  A coarse level over the `Empty`/`Solid` chunk flags is the obvious next step.
- **A fast replan interval discards most of every path.** With 1 Hz replanning and an ~9 m/s
  agent, each path is superseded after about one segment: measured `wpIndex == 2` in **98.7%** of
  samples across 483 paths, several of which had up to 7 waypoints. Everything past the second
  waypoint was computed and thrown away. Scale the replan interval to how far the agent actually
  travels per cycle rather than to wall-clock.
- **Chunk sampling is atomic within one `Pump`.** A worst-case chunk (`maxProbesPerChunk`, default
  2048) is therefore a worst-case single-frame cost. Making the level-order sampler resumable
  across frames is the planned fix.
- **No local avoidance and no path following.** This plans; it does not steer.
- **The agent is a capsule on straights and a sphere at corners; the AV is neither.** Confirmed
  in-game 2026-08-15: a large AV avoids major geometry correctly but sometimes clips small things.
  The mechanism is narrower than "the agent is a sphere":

  `Planner::LineOfSight` walks **every voxel** along a segment (Amanatides–Woo) requiring
  `clearance >= blockThreshold` at each. That is exactly a **swept-sphere** test, and a swept
  sphere is a capsule. So along any straight segment the planner already validates a capsule whose
  axis is the direction of travel. For a vehicle that flies nose-first, **the vehicle's length is
  therefore already accounted for by the sweep** — `agentRadius` should be sized to the
  vehicle's *cross-section* (the larger of half-width and half-height), **not** half its length.
  Sizing it to half-length is not "safer"; it just makes the AV refuse gaps it could fly through.

  The real gap is at **bends**. Where the path turns, an elongated body rotates, and a rotating
  box sweeps a volume strictly larger than the capsule — the nose and tail swing outside the
  validated corridor. Clipping should therefore concentrate at corners, not on straight passes.
  The targeted fix is extra clearance at turning waypoints, scaled by half-length and turn angle
  (see "Where this goes next"), which is far cheaper than planning in full (x, y, z, yaw)
  configuration space.

  **Correction (2026-08-15):** an earlier revision of this section claimed sub-voxel-thin geometry
  may fail to rasterize. That was wrong, and the reasoning was backwards. `RasterTriangle` marks a
  voxel solid when a triangle comes within `kHalfDiagonal` (`sqrt(3)/2` ≈ 0.87 voxels) of the
  voxel's **centre**, and iterates the triangle AABB expanded by that same amount. Since the
  farthest point inside a voxel from its centre is exactly `sqrt(3)/2` voxels, *any* triangle
  intersecting the voxel at all passes the test. The rasteriser is **conservative — it slightly
  over-blocks and does not miss thin geometry.** A 2 cm railing still marks its voxel solid.
  Under-blocking does not come from the bake.
- **Probes go through RTTI `ExecuteFunction`.** Pointers are resolved once and cached, but the
  per-call stack setup remains. `IWorldProbe` is the seam where a direct native call drops in.

## Shipping

Per the workspace checklist: every log site routes through the single `Log()` in
`src/game/Log.hpp`. To silence a shipping build, set `kLoggingEnabled = false` — the guard is
`if constexpr`, so both the call and the string formatting disappear. It is currently **on** for
bring-up.
